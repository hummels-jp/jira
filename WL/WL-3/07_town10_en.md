| Element | Field | Example Value | Description |

Difference from [2.5 ElevationProfile](#25-elevationprofile): elevation describes the **vertical** undulation of the road surface, while superelevation describes the **lateral** tilt of the road surface.

##### Field Descriptions for the Example

Each `<laneOffset>` segment defines the lateral offset `offset` as a cubic polynomial in the local coordinate `ds = s - s_segment-start`:

> **offset(ds) = a + b·ds + c·ds² + d·ds³**

| Element | Field | Example Value | Description |
| --- | --- | --- | --- |
| `<laneOffset>` | `s` | `0.0` / `9.9999999999997868e-2` (≈0.10 m) | Starting s-coordinate of this offset segment on the road reference line (meters); segments connect in order along s. |
| `<laneOffset>` | `a` | `6.6349999999999962e+0` (≈6.635 m) | Polynomial constant term: the lateral offset of the lane center relative to the reference line at the segment's start (meters). It is non-zero in this example, meaning the lanes as a whole are offset from the reference line by about 6.635 m. |
| `<laneOffset>` | `b` | `0.0` | First-order coefficient: the first-order rate of change of the offset with ds; 0 means the offset is constant. |
| `<laneOffset>` | `c` | `0.0` | Second-order coefficient: the curvature term of the offset change. |
| `<laneOffset>` | `d` | `0.0` | Third-order coefficient: higher-order change, ensuring smooth transitions between segments. |

> Note: `laneOffset` shifts the **center reference line shared by all lanes** (as distinct from the `<width>` definition of an individual `<lane>`). For ordinary roads (such as `Road 9`), the lane center usually coincides with the reference line, with `a=0`; whereas connecting roads inside junctions (such as `Road 111`) often need to shift the entire group of lanes to the correct position within the junction, so `a` takes a non-zero constant (≈6.635 m in this example, with `b/c/d` being 0 meaning the offset is constant throughout). There are approximately 768 `<laneOffset>` segments in the entire map.

#### 8.2.10 Unified Fields and Parsing Strategy

- These objects can all be parsed via the following generic fields:
  - `id`, `name`, `s`, `t`, `zOffset`, `hdg`, `orientation`, `type`, `width`, `length`
  - `outline`: if present, represents the geometric outline of the object in the local coordinate system
  - `validity`: if present, limits the object's effective scope over specific lanes or road segments
- Therefore, adopting the same parsing and statistical strategy as `StopLine` for these types allows unified handling of road objects such as surface markings, crosswalks, pedestrian crossings, guide arrows, and marking regions.
