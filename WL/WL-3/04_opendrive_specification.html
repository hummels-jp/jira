OpenDRIVE 数据结构规范

1. 核心数据板块 (Core Data Blocks)

OpenDRIVE 文件由多个层级的数据板块组成，分别管理路网的几何逻辑、物理设施及拓扑关系。

板块 功能 关键内容
Header全局定义坐标原点、投影、版本信息。
Roads几何基准参考线 (Reference Line)、几何多项式定义。
Lanes车道逻辑车道拓扑、宽度、线型属性、速度规则。
Junctions路口管理连接路网、相位控制参考。
Objects物体定义静态物体几何、语义属性、碰撞盒。
Signals交通指示标志牌、信号灯逻辑。

2. 对象类型规范 (Object Classifications)

在 <objects> 板块中，通过 type 属性定义静态交通物体，以下是主要类型规范：

对象类型 (Type) 主要描述 几何特征
crosswalk人行横道平面区域，BoundingBox 或 Outline。
pole电线杆/杆状物垂直实体，用于支撑。
barrier护栏具有体积的线性障碍物。
building建筑物静态复杂几何轮廓。
street lamp路灯垂直照明设施。
traffic island交通安全岛路面分流平面区域。
pothole坑洼路面破损标记。
parking space停车位路面停车区域。

3. crosswalk (人行横道) 结构与示例

在 OpenDRIVE 中，crosswalk 被定义为一种平面对象。它通过 <outline> 定义精确的几何多边形，或者通过 <border> 定义其边界。

基本结构：

<object type="crosswalk" id="101" s="50.0" t="0.0">
    <outlines>
        <outline>
            <cornerRoad s="0.0" t="0.0" dz="0.0"/>
            <cornerRoad s="5.0" t="0.0" dz="0.0"/>
            <cornerRoad s="5.0" t="2.0" dz="0.0"/>
            <cornerRoad s="0.0" t="2.0" dz="0.0"/>
        </outline>
    </outlines>
</object>
  • 关键属性：s 和 t 定义了该对象相对于道路参考线的起始基准点。
  • 几何构成：通过 cornerRoad 定义了一系列的顶点，闭合后即形成人行横道的平面轮廓。
  • 仿真意义：仿真器读取此结构，生成具有碰撞检测功能的平面几何，从而实现行人通行逻辑的物理映射。

4. OpenStreetMap (OSM) 路网描述结构

OpenStreetMap 使用基于拓扑的图结构来描述道路网络，其核心由 Node（节点）、Way（路径）和 Relation（关系）构成，与 OpenDRIVE 的路径/车道模型有本质区别。

OSM 元素 描述 对应关系
Node 地理坐标点 (Lat/Lon) 定义了路网的物理位置，类似于 OpenDRIVE 的参考点。
Way 有序节点列表 代表道路线或道路区域，通过节点有序连接形成几何形状。
Relation 逻辑组合与约束 将多个 Way 组合成复杂的逻辑道路或区域（如斑马线区域、车道集）。
Tags 语义键值对 (Key-Value) 用于定义道路类型、限速、通行权限（如 highway=primary）。

注意：由于 OSM 本质是图数据而非工程化几何模型，从 OSM 转换到 OpenDRIVE 时，必须通过复杂算法进行车道中心线计算、拓扑缝合及语义映射，这也是造成转换过程中容易出现非闭合路网的主要原因。

5. OpenStreetMap (OSM) 道路附属物类型 (Highway Features)

在 OSM 中，道路附属物通常通过特定的 Key=Value 标签定义在 Node 或 Way 上。以下是常见且关键的附属物类型：

  • 行人与交通设施：
    • crossing=zebra：斑马线。
    • traffic_signals=yes：交通信号灯。
    • traffic_sign=*：交通标志牌（如限速、让行）。
  • 物理路面与结构：
    • kerb=*：马路牙子/缘石。
    • barrier=*：屏障（如 bollard 立柱、guard_rail 护栏）。
    • surface=*：路面材质（如 asphalt 沥青、paved 已铺装）。
  • 环境与景观：
    • natural=tree：树木。
    • building=yes：建筑物。
    • street_lamp=yes：路灯。

注意：由于 OSM 标签体系极其广泛且具有高度的可变性，在将其转换映射为 OpenDRIVE 的 <objects> 时，通常需要构建一个转换规则映射表，以处理非标准化的 Tag 值。

6. OpenStreetMap (OSM) 斑马线 (Crossing) 描述与示例

在 OSM 中，斑马线通常通过在 Way 上附加 highway=crossing 标签，并配合 crossing=zebra 来表示。该方式将斑马线视为道路网的一个节点或一段特殊路径。

OSM 数据描述逻辑：

<way id="5001">
    <nd ref="1001"/>
    <nd ref="1002"/>
    <tag k="highway" v="crossing"/>
    <tag k="crossing" v="zebra"/>
    <tag k="width" v="3.0"/>
    <tag k="tactile_paving" v="yes"/>
</way>
  • 标记方式：highway=crossing 定义了该对象为横越道路的设施；crossing=zebra 具体明确了斑马线的语义类型。
  • 关键属性：
    • width: 斑马线的宽度。
    • tactile_paving: 是否铺设了盲道/触觉铺装，这对于评估行人友好度非常重要。
  • 转换挑战：在向 OpenDRIVE 转换时，需要根据 Way 的几何线型和节点关联关系，将其映射为 <object type="crosswalk">，并计算其在参考线坐标系下的坐标偏移（s, t）。

通过对 negishi.osm 源数据的统计分析，可以明确该数据集在不同类别对象上的标注完整度。这对评估 OpenDRIVE 转换潜力至关重要。

建筑物 (building)232高 (完备)
自然景观 (natural)81高 (完备)
路面材质 (surface)105高 (完备)
信号灯 (traffic_signals)26中 (需校验)

结论： 该地图数据在处理斑马线及建筑物几何映射时具有较高可行性，但缺乏路边缘约束 (kerb) 及辅助照明 (street_lamp) 数据，在转换至 OpenDRIVE 的 <objects> 板块时，若缺乏物理边缘仿真，可能需要后期根据道路线型进行自动补全。

8. Map_Sendai.xodr 语义标注分析

通过对 Map_Sendai.xodr 进行数据审计，发现该文件中虽然包含大量物体对象，但由于转换脚本的配置缺陷，导致语义标签失效。

  • 问题现象：共定义 76 个 <object>，但其 type 属性几乎全被错误标记为 "none"。
  • 技术后果：仿真器（如 CARLA/RoadRunner）无法识别斑马线、车道标记等交通逻辑，导致仿真环境中这些功能不可用。
  • 修复路径：利用文件中保留的 name 属性（如 Stencil_ArrowType...）作为映射键，编写批处理脚本将 type="none" 修正为规范的语义类别。
